## 一、软件名称、品牌定位与演进使命


### 1.1 软件全称与字义内涵

软件定义：软件官方全称为「睿链进销存与往来管理系统」（英文名称：Ruilian Enterprise Resource & Settlement Management System，简称“睿链”或“RUILIAN ERP”）。软件命名蕴含着明确的商业与技术双重诉求：

- “睿”（Insight & Intelligence）：体现经营分析、商业洞察与智能辅助决策。系统不仅记录出入库流水，更通过价格决策引擎、毛利核算、账龄穿透分析与全景预警雷达，帮助经营管理层洞悉库存结构与资金周转瓶颈，提升企业精细化管控效能。
- “链”（Linkage & Chain）：体现供应链与资金链的强闭环链路。系统将商品采购、验收入库、销售订单占用、物流出库、往来应收应付、资金收付核销等核心业务无缝串联，消除传统企业管理中“货与账割裂”、“单据无序变更”的信息孤岛，构建坚固的业务闭环链条。

### 1.2 商业定位与未来演进路线

## 二、项目总体定位与业务边界


### 2.1 适用行业与企业规模

系统具备深度的行业通用性与业务适配弹性，特别针对以下行业场景进行深度优化：

- 批发与渠道分销：多品类批发商（快消品、五金机电、电子数码、汽配、日用百货等），具备多仓多批次、阶梯价格、大客户信用账期赊销特征；
- 商贸零售一体化：门店前店后仓，兼顾零售现场开单收款（现销全自动核销）与批发客户批量出库；
- 委托代销与联营：拥有直营总仓与外部委托经销商，需要对发出未结商品实施“委托代销仓”资产管控，并按实际销售对账开单结算；
- 轻工装配与拆解：外购标准零配件，通过简单 BOM 组装形成最终销售商品，或将大包装商品拆分为散装组件，需自动结转产出成本；
- 集团化与连锁加盟：总部统一管控平台，各子公司、分公司或加盟商作为独立租户物理沙箱运行，互不干扰、独立核算。

### 2.2 核心业务四大闭环全景

系统摒弃传统软件各自为政的数据分散模型，在架构底层建立严格的四大业务闭环：

- 1. 货物流闭环：商品主档驱动规格批次 → 采购订单执行入库增加物理现存量 → 销售订单预占可用库存 → 销售出库扣减物理量并释放预占 → 仓间调拨/盘点差异调整，每一笔库存变动均具备双向可追溯单号与 InventoryTransaction 流水。
- 2. 资金流闭环：销售出库自动生成应收账款（AR Bill）/ 采购入库自动生成应付账款（AP Bill） → 资金收付结算单（Settlement） → 依据到期日先进先出自动核销或多对多手动核销 → 预收预付沉淀结转 → 贷项冲账（Offsets） → 往来对账与账龄分析。
- 3. 控制流闭环：六级价格决策优先级引擎 → 最低销售限价底线拦截 → 客户信用额度与账期强校验 → 库存上下限、呆滞料与单据异常六大预警雷达 → 预警确认（warning_ack）闭环。
- 4. 平台管控闭环：SaaS Database-per-Tenant 物理数据库独立沙箱 → 毫秒级存储配额统计与写拦截 → 平台超级管理员专属身份（huxinkui）与安全防御体系 → 租户权限强隔离与无感穿透巡检。

### 2.3 业务边界与系统假设

> 【系统边界与设计底线】
> 1. 本系统专注于进销存及往来资金核算领域，不直接替代总账会计凭证软件（如总账明细账、固定资产折旧计提、科目余额表）。系统通过精准的原始业务单据与往来核销明细，提供标准化接口与凭证数据导出能力，供外部专业财务软件（如用友、金蝶）无缝集成。
> 2. 严禁业务人员越过业务单据直接篡改库存余额或账面金额。系统所有状态变更必须由具有明确审计来源的业务事件驱动。
> 3. 系统保证数据最终强一致性，事务执行遵循严格的 ACID 特性，不允许单边账（如库存扣减成功但流水未写入、或应收账款生成但销售单据回滚）。

### 3.2 高精度定点计算与防浮点误差设计

精度设计原则：在进销存与往来账务系统中，浮点数运算（如 IEEE 754 规范的 float32/float64）会导致灾难性的精度损失（例如 0.1 + 0.2 = 0.30000000000000004），随着业务单据的大规模累加，将导致账实不符与金额单边分钱偏差。系统在底层架构上彻底摒弃浮点数，全面推行高精度定点整数机制：

- 货币金额定点化（Scale = 100）：所有货币金额字段（如单据总额 total、成本金额 cost、账单金额 amount、结算金额 settled 等）在数据库与内存中统一以「分」（Cent，即 0.01 元）作为整数（int64）存储。前端显示时通过除以 100 格式化为标准两位小数，接收输入时乘以 100 转换为整数，杜绝一切四舍五入累计误差。
- 数量与单价高精度定点化（Scale = 10000）：商品数量（quantity）与单价（price）支持最多四位小数（例如单价 12.3456 元，数量 0.0025 件）。系统在内部采用「万分之一」（Scale = 10000）的定点整数进行运算与存储。在金额结算计算时，严格执行定点乘除规范：金额分 = (数量 × 单价 + Scale/2) / Scale，保证精确的四舍五入取整。
- 溢出安全防护（Max Value Guard）：系统在 models.go 中定义全局极值校验（MaxValue = 900,000,000,000,000 分，即 9 万亿元人民币），在算术运算前执行溢出前置阻断，防止 64 位整数溢出导致资金金额异常翻转。

### 3.4 三大部署运行拓扑模型

为满足企业从单机初创到大型连锁、乃至公网云端托管的不同发展阶段，系统在架构上设计了三种标准部署模式：

- 模式 A：独立客户端单机离线部署（Desktop Mode）：采用 Electron 跨平台容器打包，内嵌编译好的 Go 独立二进制服务与纯 Go SQLite 引擎。前端资源与数据库随安装包落地于用户的 `%APPDATA%\RuilianERP` 目录。不依赖系统环境中的外部浏览器、Node.js、Python 或外部数据库，断网环境下依然 100% 正常运行，提供最极致的免运维体验。
- 模式 B：局域网协同服务器部署（LAN Multi-Client Mode）：将 Go 服务端部署在企业内部局域网服务器（Windows Server 或 Linux），数据库开启 WAL 高速读写模式。局域网内各 PC 客户端通过浏览器或桌面客户端指定服务器局域网 IP 接入，实现企业内部多部门、多仓库、采购与财务协同作业。
- 模式 C：公网 SaaS 多租户云端托管部署（Cloud SaaS Mode）：在公网云服务器（如阿里云、腾讯云等）部署，前端通过 Nginx 挂载 SSL/TLS 证书并执行动静分离，后端开启 Database-per-Tenant 物理数据库多租户沙箱模式。超级管理员通过专属总控后台集中监控所有租户，各分支机构或客户租户通过专属子域名或租户代码进行公网安全访问。

## 五、基础资料模块深度设计


### 5.1 商品主档架构与关键控制属性

商品是进销存流转的核心客体。系统在 `base_records` 表中以 `kind='product'` 统一存储商品主档，其关键属性分为基础信息、单位规格、库存控制与财务价格四大维度：

| 属性分类 | 核心字段 | 数据类型/约束 | 业务含义与系统控制逻辑 |
| --- | --- | --- | --- |
| 基本标识 | name, code | TEXT NOT NULL, UNIQUE | 商品名称与唯一编码。编码可由操作员手动录入，若留空则由系统编号生成器自动赋码。 |
| 分类与品牌 | category_id, brand | INTEGER, TEXT | 所属树形分类（支持多层级目录展开）与商品品牌，用于多维报表统计与筛选过滤。 |
| 规格与条码 | spec, barcode | TEXT, TEXT | 规格型号（如“500ml/瓶”、“XL”、“标准型”）与 EAN-13/自定义条形码，支持扫码枪快速开单。 |
| 计量单位体系 | unit, aux_unit, unit_ratio | TEXT, TEXT, INT | 基本单位（如“个/件/KG”）与辅助单位（如“箱/包”）；unit_ratio 为换算比例。入账统一按基本单位结转。 |

> 【商品主档安全原则】
> 商品主档引用完整性保护底线：
> 1. 凡是已被采购单、入库单、销售出库单、调拨单或库存流水引用的商品，系统严格禁止修改其计量单位（unit）、批次管理标志（enable_batch）和序列号管理标志（enable_serial），防止底层历史台账数据断裂失真。
> 2. 商品不支持直接物理删除，系统提供停用机制（active=0）。停用后，商品在新增开单选择器中自动过滤隐藏，但历史已审核单据与报表查询中完整保留历史信息。


### 5.2 往来单位资料（客户与供应商）设计

往来单位分别以 `kind='customer'` 和 `kind='supplier'` 存入基础主档，支撑销售赊销控制与采购账期管理：

- 客户主档（Customer）：包含客户编码、名称、分类、价格等级（如“VIP一级客户”、“二级代理商”、“普通零售客户”）、信用额度上限（以分为单位）、结算账期天数（如 30 天，用于推算单据到期日 due_date）、专属折扣率（如 95%）、纳税人识别号与开票信息。
- 供应商主档（Supplier）：包含供应商编码、名称、分类、默认结算账期天数、开户银行名称与账号、供货评价等级。采购开单时系统依据供应商账期自动推算付款到期日并纳入应付账款管理。

### 5.3 仓储物流体系与多库位模型

系统建立分级物理与逻辑仓储网络体系（`kind='warehouse'`, `kind='location'`）：

- 仓库类型分类：实物普通仓库（企业真实物理库房，如“北京总仓”、“上海中心仓”）、委托代销仓（记录发出但尚未结算的代销商品资产）、报废待检仓（不合格品与维修退回隔离仓）。
- 精准库位坐标：仓库内部划分货区、货架与货位。出入库单据明细可细化至 location_id 级别，满足精准货位盘点与快速拣货路径规划需求。

### 5.4 单据自动编号序列引擎（document_sequences）

业务单据编号具备法务效力与唯一性，系统在 `document_sequences` 表中实现高并发原子递增发号引擎：

- 统一编号规则：前缀代码（Prefix） + 日期时间戳（YYYYMMDD） + 4 位自增流水号（0001, 0002...）。例如：采购订单为 `PO-20261015-0001`，销售出库单为 `SDN-20261015-0002`，收款单为 `REC-20261015-0001`。
- 高并发防跳号机制：在数据库事务内通过 `INSERT ... ON CONFLICT(prefix, day) DO UPDATE SET value = value + 1 RETURNING value`，保证即使在多用户并发开单场景下，单据编号绝对连续且绝不重复。

    +-------------------+                        +-------------------+

                                      +--------------------+--------------------+

### 6.2 采购订单预留与分批执行控制

采购订单（purchase_order）代表企业对外部供应商的订货契约，其核心规则如下：

- 订单状态与影响：采购订单审核通过后，仅作为后续入库的业务凭证，系统不增加物理库存数量，也不在财务账上确认应付账款，仅计入采购在途（In-Transit）承诺。
- 分批多次入库追踪：支持单张采购订单分多批次验收入库。系统在明细行中维护 `source_item_id` 建立上下游强追溯，实时计算 `累计已入库数量`。当累计入库量达到订单承诺量时，采购订单状态自动由 `in_progress` 跃迁为 `completed`；若供应商超量供货，系统支持超额比例拦截（默认不允许超单入库）。

### 6.3 采购入库与成本确认原子事务

采购入库单（purchase_receipt）是库存与资金变化的触发原点。审核采购入库单时，系统在一个排他数据库事务内原子执行以下操作：

- 1. 增加物理库存：在 `inventory` 表中将对应商品的物理现存量（quantity）累加入库数量；
- 2. 移动加权成本计算：根据原库存结存金额与本次入库金额，重新计算该商品在该仓库库位的移动加权平均成本单价，更新 `inventory.value`；
- 3. 写入不可逆流水：在 `inventory_transactions` 表中写入正向记账流水，记录变动前后数量、成本单价与操作员信息；
- 4. 确认应付账款：在 `bills` 表中创建供应商应付账单（side='ap'），金额为入库含税总额，到期日根据供应商默认账期自动计算；
- 5. 序列号生命周期入库：若采购商品启用了序列号管理，在 `inventory_serials` 中批量插入序列号并将其状态置为 `in_stock`。

### 6.4 采购退货与换货的原单追溯机制

采购退货（purchase_return）与换货（purchase_exchange）涉及实物资产流出与供应商账务反向冲销：

- 原单强绑定原则：退货开单必须选择对应的原采购入库单（GRN）。明细行必须绑定原单明细行，校验单行累计退货数量 <= (原入库数量 - 累计已退数量)。退货单价强制沿用原采购入库单价，杜绝人为输入虚假退货价格导致的账目虚盈实亏。
- 退货账务处理：采购退货审核后，扣减对应商品物理库存，写入负向库存流水；同时在 `bills` 表中自动生成一笔负向应付账单（负金额贷项单），财务人员可在往来模块中将其与正向应付账单直接对冲或执行退款登记。
- 换货差额平衡：换货单由“退回行”与“换入行”两组明细构成。退回行扣减库存，换入行增加库存。两者金额差额自动转化为应付差额账单进行补差或冲销。

### 7.2 销售订单预占（Stock Reservation）引擎

在多渠道并发销售场景下，防止客户下单后因并发冲突发生“超卖”是系统的核心职责：

- 锁定可用量：销售订单审核通过后，系统在 `stock_reservations` 表中插入一条预占记录，并将 `inventory.reserved` 数量累加对应订购量。此时：`可用库存 (Available) = 物理现存量 (Quantity) - 预占用量 (Reserved)`。
- 出库释放预占：当下推生成销售出库单（SDN）并审核时，系统释放该订单在 `stock_reservations` 中的预占记录（reserved 减少），同时扣减真实的物理现存量（quantity 减少）。
- 订单作废回退：若销售订单发生取消、作废或关闭，系统自动执行反向事务，完全撤销其预占量，恢复商品可用库存。
- 直接出库可用量前置拦截：当操作员直接创建无前序订单的快速销售出库单时，系统执行排他校验：`inventory.quantity - inventory.reserved >= 本次出库数量`。一旦可用库存不足，即使物理总库存充裕，系统亦严格拦截并报错 `400 VALIDATION: 可用库存不足（存在其他订单预占），禁止出库`。

### 7.3 批发赊销与现销零售双重模式

- 赊销模式（Credit Sales）：常规 B2B 批发业务。销售出库单审核后，生成客户应收账单（bills 表 side='ar'），金额进入客户应收账款与账龄分析，受客户信用额度与账期强管控约束。
- 现销模式（Cash Sales）：面向现金、微信、支付宝即时收款的零售与柜台现销业务。操作员在销售出库界面勾选「现销」标志并录入实收金额。系统审核出库时，在同一事务内：扣减库存 → 生成应收账单 → 自动创建客户收款单（settlements 表 side='ar'） → 触发 100% 自动核销引擎。系统瞬间完成出库与回款闭环，无需财务人员二次手动对账。

### 7.4 销售退货与成本原路精确恢复

传统进销存软件在销售退货入库时，常采用“当前最新进价”或“退货时移动平均价”重新计入库存，导致企业利润严重失真。睿链在架构上实施严格的成本还原机制：

> 【销售退货核心原则】
> 销售退货成本还原三原则：
> 1. 销售退货单（sales_return）必须强绑定原销售出库单（SDN）的明细行项 ID（source_item_id）；
> 2. 退货入库时，该商品的入库成本必须严格等于原出库单明细行当时结转的真实单位销售成本（cost_unit），严禁采用退货时的市场价或当前移动均价入账；
> 3. 系统将原出库成本与数量重新加权合入当前库存资产中，确保无论业务如何退换货，商品历史总成本与毛利计算始终保持数学闭环。


### 7.5 委托代销（Consignment）完整闭环

系统专为联营商场、外部经销商铺货场景设计了委托代销标准流转闭环：

- 1. 委托发货：委托发货单（consignment_order）：将商品从实物自有总仓调拨至该客户专属的“委托代销仓”。该步骤仅发生物理位移，不确认销售收入，不扣减企业资产，不生成应收账款。
- 2. 代销结算：代销结算单（consignment_settlement）：代销方定期上报实际售出报表后，业务员以此单据从委托代销仓正式扣减库存，并根据合同约定的结算价格确认销售收入，同时在 `bills` 表中生成应收账款。
- 3. 委托退回：委托退回单（consignment_return）：代销期限届满或未售出商品，通过此单据从委托代销仓平移回实物总仓，恢复常规库存。

## 八、库存与仓储履约模块深度设计


### 8.1 四维库存核心坐标模型

系统在底层 `inventory` 表建立严密的四维空间定位模型，任何一条库存记录均由以下四元组唯一确定：

- 维度 1：商品（product_id）：唯一指代具体的商品主档（base_records 表 id）；
- 维度 2：仓库（warehouse_id）：物理仓库（如“北京主仓”、“广州成品仓”）；
- 维度 3：库位（location_id）：货架/货区/货位编号（未启用库位时默认为 0）；
- 维度 4：批次（batch）：生产批次号（如“B20261015-01”），未启用批次时默认为空字符串 ''。
数据库施加物理复合主键约束：`UNIQUE(product_id, warehouse_id, location_id, batch)`，从根本上防止同一坐标出现多条重复记录导致库存分裂。


### 8.2 移动加权平均成本核算引擎

系统采用行业标准的移动加权平均成本算法（Moving-Weighted Average Cost），在每次发生正向入库时动态更新单位结存成本：

```text
【入库重算公式】：
                 原结存总金额 (V_old) + 本次入库数量 (Q_in) × 本次入库单价 (P_in)
    新结存成本 = -----------------------------------------------------------------
                               原结存总数量 (Q_old) + 本次入库数量 (Q_in)

    【出库结转公式】：
    本次出库成本金额 = 本次出库数量 (Q_out) × 当前结存单位成本 (Cost_current)
    新结存总金额 (V_new) = 原结存总金额 (V_old) - 本次出库成本金额
```

边界处理：对于零库存再入库场景：若 $Q_{old} = 0$，新单位结存成本直接等于本次入库单价 $P_{in}$。
系统严格遵循全定点整数乘除运算，保留万分之一单价精度与分级金额精度，每次计算的余数纳入库存结存金额中，防止微小分钱误差长期累积。


### 8.3 仓间调拨（Stock Transfer）

调拨单（inventory_transfer）用于不同仓库或库位之间的商品调配。系统在单个事务内原子完成调出与调入：

- 调出扣减：校验调出仓的可用库存是否充裕，以当前调出仓的移动加权平均成本扣减调出仓库存数量与金额，写入负向流水；
- 调入增加：以调出单据所结转的实际成本金额，全额增加到调入仓的结存数量与金额中，重新加权调入仓单位成本，写入正向流水；
- 资产守恒：两端原子完成，全过程企业整体库存总资产保持严格守恒，无资金外溢与亏空。

### 8.4 盘点管理与差异纠错（Stocktaking）

盘点是纠正账实差异、防范仓储损耗的核心手段：

- 1. 提取账面快照：盘点发起时，系统读取目标仓库所有四维坐标的当前账面库存（book_quantity），并在单据明细中静态固化；
- 2. 录入实盘数据：仓管人员线下实盘清点后，录入实盘数量（quantity）；
- 3. 差异审核与流水过账：系统自动计算盘盈盘亏差异量：`差异 = 实盘数量 - 账面数量`。审核时，若盘盈则按当前成本自动增加库存并写入盘盈流水；若盘亏则扣减库存结存并写入盘亏流水，差异损益计入报表；
- 4. 动态并发冲突保护：若在盘点单保存至审核期间，该四维坐标发生了其他单据的出入库变动，系统在审核时通过版本校验拒绝过账，并提示仓管人员重新提取最新账面库存进行复核，杜绝并发篡改引发的历史脏数据覆盖。

### 8.5 BOM 组装与拆分（Assembly & Disassembly）

轻工生产与套装销售企业常常涉及商品的组装与拆解：

- 组装单（Assembly）：组装单由多个「组件出库明细」和一个「成品入库明细」构成。审核时，系统扣减所有组件库存，计算所有消耗组件的总成本金额：$TotalCost = \sum (Q_{sub} \times Cost_{sub})$。该总成本全额赋予产出的成品入库明细，成品的单位入库成本即为 $TotalCost / Q_{product}$。
- 拆分单（Disassembly）：拆分单由一个「母件出库明细」和多个「子配件入库明细」构成。系统扣减母件库存并结转其历史总成本。子配件入库成本支持按「参考价格权重」或「数量权重」在子配件之间进行科学分摊，确保拆分前后企业库存总价值严格相等。

## 九、往来与资金管理模块深度设计


### 9.1 应收应付（AR/AP）双向对称数据模型

系统在底层采用高度优雅的对称结构统一管理客户应收（AR）与供应商应付（AP）：

- 业务账单表（bills）：记录由销售出库（side='ar'）或采购入库（side='ap'）产生的原始应收应付账单。字段包含：document_id（绑定业务单据）、partner_id（往来客户/供应商）、amount（账单原始总额）、settled（已核销金额）、due_date（款项到期日）、state（active 未结清 / settled 已结清 / cancelled 已作废）。
- 资金结算单表（settlements）：记录资金的真实流入与流出。客户收款单（side='ar'）与供应商付款单（side='ap'）。字段包含：document_id、partner_id、amount（实收/实付金额）、allocated（已分配核销金额）、state。
- 资金核销关系表（writeoffs）：记录结算单与账单之间的多对多核销关系。字段包含：settlement_id、bill_id、amount（本次核销金额）、created_by、reversed（是否已反审核撤销）。

### 9.2 资金收付与自动核销（FIFO Auto-Writeoff）算法

资金核销不仅支持财务人员手动在界面上跨单据、多账单精准勾选分配，更内置了业界领先的高效自动核销引擎：

```text
【先进先出自动核销算法流程】：
    输入：往来单位 ID (partner_id), 业务方向 (side: ar/ap), 本次实收/实付金额 (SettlementAmount)
    1. 开启数据库排他事务 BEGIN IMMEDIATE;
    2. 查询该往来单位所有未结清账单：
       SELECT * FROM bills WHERE partner_id=? AND side=? AND state='active' 
       ORDER BY due_date ASC, id ASC;
    3. 剩余待核销金额 Remainder = SettlementAmount;
    4. FOR EACH bill IN bills:
           IF Remainder <= 0 THEN BREAK;
           未结金额 Unsettled = bill.amount - bill.settled;
           本次冲销 Apply = MIN(Remainder, Unsettled);
           // 写入核销流水
           INSERT INTO writeoffs(settlement_id, bill_id, amount, created_by, created_at)
           VALUES(..., Apply, ...);
           // 更新账单已核销金额
           bill.settled += Apply;
           IF bill.settled >= bill.amount THEN bill.state = 'settled';
           Remainder -= Apply;
    5. 结算单记录已分配金额：settlement.allocated = SettlementAmount - Remainder;
    6. IF Remainder > 0 THEN:
           // 超额款项自动沉淀为该单位的「预收款」或「预付款」余额
           系统将 Remainder 保留在当前结算单中，待后续新单据产生时直接点击核销;
    7. 提交事务 COMMIT;
```


### 9.3 贷项冲抵与双向对冲（Offsetting）机制

在实际商贸活动中，退货、折扣或对账差额常常产生负账单或退款单，系统提供完善的免资金流动对冲机制：

- 账单间对冲（bill_offsets）：销售退货产生的应收负账单，可直接与该客户的历史正向未结应收账单在 `bill_offsets` 表中对冲冲平，无需先退款再收款。
- 结算单间对冲（settlement_offsets）：客户之前支付的预收款或退款结算单，可与后续收款单在 `settlement_offsets` 表中相互对冲冲销。
- 反核销与错误冲正：若核销操作存在人为录入失误，系统支持「撤销核销」（Un-writeoff）。系统将 `writeoffs.reversed` 标志置为 1，原子回退账单的 `settled` 金额与结算单的 `allocated` 金额，恢复账单为 `active` 状态，并完整保留撤销审计轨迹。

### 9.4 客户信用额度与账期强控制模型

为有效防范客户拖欠货款与坏账风险，系统在销售开单与审核全流程中嵌入信用风险敞口强校验：

```text
【客户当前信用敞口计算公式】：
    当前敞口风险值 (RiskExposure) = 历史未结清应收账单总额 (UnsettledBills)
                                 + 审核中且尚未出库的销售订单总金额 (PendingOrders)
                                 - 客户沉淀的可用预收账款余额 (AdvanceReceipts)

    【开单与审核拦截规则】：
    IF 客户设置了信用额度 (CreditLimit > 0):
        IF RiskExposure + 本次单据金额 > CreditLimit:
            拦截报错: HTTP 400 VALIDATION: 客户信用额度超限 (当前敞口已达上限)，禁止开单/审核！
    IF 客户存在严重逾期账款 (OverdueDays > AllowToleranceDays):
        拦截报错: HTTP 400 VALIDATION: 该客户存在超期未付应收账单，系统已锁定赊销权限！
```


### 9.5 应收账龄分析多维区间模型

系统依据应收账单的实际到期日（due_date）与当前日期的差值，构建精确到日的账龄分析矩阵：

| 账龄区间 | 逾期判定标准 | 风险等级 | 系统管控与催收建议 |
| --- | --- | --- | --- |
| 正常账期内 | 当前日期 <= 到期日（剩余账期天数 >= 0） | 正常安全 | 正常业务跟进，可继续享受常规授信额度。 |
| 逾期 1~30 天 | 到期日 < 当前日期 <= 到期日 + 30 天 | 一级关注 | 轻度逾期，系统在工作台提示预警，业务员跟进日常对账催收。 |
| 逾期 31~60 天 | 到期日 + 31 天 <= 当前日期 <= 到期日 + 60 天 | 二级预警 | 中度逾期，系统收紧新增赊销额度，开单需主管审批。 |
| 逾期 61~90 天 | 到期日 + 61 天 <= 当前日期 <= 到期日 + 90 天 | 三级高危 | 严重逾期，系统强制冻结该客户所有赊销权限，仅支持全款现销。 |
| 逾期 90 天以上 | 当前日期 > 到期日 + 90 天 | 四级呆坏账 | 极度高危，系统自动上报预警中心，移交法务与专人清收处理。 |


## 十、价格决策与折扣引擎模块深度设计


### 10.1 六级价格决策优先级金字塔

系统在 `price_rules` 表与基础主档中构建了一套灵活强大的动态价格决策引擎。在销售或采购录入商品明细时，系统按照严格的优先级顺序从高到低逐级匹配，一旦命中立即终止后续查找：

| 优先级层级 | 规则类型 (kind) | 判定条件与匹配维度 | 业务应用场景 |
| --- | --- | --- | --- |
| Level 1 (最高) | 客户专属约定价 | product_id + customer_id 强匹配，且在生效期内 | 核心战略大客户合同一口价、框架协议约定采购价格。 |
| Level 2 | 客户等级价格 | product_id + customer_level（如 VIP1/经销商/批发商） | 不同渠道分销等级的标准化差异定价体系。 |
| Level 3 | 限时促销特价 | start_date <= 当前业务日期 <= end_date，且 active=1 | 节假日促销、季末清仓特惠、厂商联动降价活动。 |
| Level 4 | 数量阶梯价格 | min_quantity <= 本次购买数量 <= max_quantity | 支持“买得越多单价越低”的批量大宗批发折扣。 |
| Level 5 | 基础销售售价 | 取自商品主档 base_records 中的 base_price | 商品常规标准销售牌价。 |
| Level 6 (保底) | 零售指导售价 | 取自商品主档 base_records 中的 guide_price | 官方零售参考价，无其他规则时的最终兜底价格。 |


### 10.2 底线价格保护（Min Price Guard）

为防范前线业务人员为了冲刺个人业绩私自大幅让利、或因失误录入超低价格导致企业巨额亏损，系统设置了不可突破的底线限价防线：

- 底线配置：在商品主档或价格规则中设定 `min_price`（最低销售限价，以分为单位）。
- 刚性拦截：在销售出库单录入或修改时，不论业务员输入何种折扣率或特批价格，折后实际成交单价 `item.price` 必须满足：`item.price >= item.min_price`。若低于底线，系统在审核时直接强行报错拦截，杜绝低于成本线甩卖的合规漏洞。

### 10.3 客户端即时试算与服务端防篡改安全校验

系统在价格交互设计上兼顾了「极致的操作流畅度」与「绝对的后端安全性」：

- 前端即时试算体验：操作员在前端选择客户与商品并修改数量后，前端异步调用 `/api/pricing/calculate` 接口。后端定价引擎即时返回推荐价格、命中的价格规则名称与折扣信息，前端界面实现无刷新即时自动填充。
- 后端防篡改强校验：前端提交的单据数据绝不作为后端记账的唯一信任源。在保存和审核单据时，后端独立重跑定价引擎与校验规则，严密防范通过 Postman、爬虫或改包工具篡改单价的行为。若发现提交价格违背最低限价，后端直接阻断并记录安全告警日志。

## 十一、预警中心与智能监控模块深度设计


### 11.1 业务预警六大雷达矩阵

系统在后台运行实时与定时智能巡检分析服务，构建覆盖仓储、资金与交易全领域的六大预警雷达：

| 预警雷达维度 | 触发阈值判定条件 | 风险危害分析 | 闭环处置动作 |
| --- | --- | --- | --- |
| 1. 库存短缺预警 | 四维库存可用量 <= 商品设定的最低安全库存 min_stock | 缺货导致订单无法及时履约交付，造成客户流失。 | 一键下推生成采购建议订单或跨仓调拨申请。 |
| 2. 库存超限积压 | 四维库存现存量 >= 商品设定的最高库存 max_stock | 资金被过度占用，仓库仓储成本激增，贬值风险高。 | 触发降价促销、放缓后续采购入库节奏。 |
| 3. 呆滞物料雷达 | 商品在库超过 N 天（默认 90 天）无任何出库销售流水 | 物料陈旧过期报废，导致企业账面资产减值坏账。 | 系统提示折价处理、返厂换货或捆绑促销组合。 |
| 4. 客户信用超额 | 客户当前风险敞口金额 > 客户授信额度 credit_limit | 客户赊销资金敞口过大，可能诱发系统性坏账逾期。 | 强制阻断新增销售赊销审核，仅支持现款现货。 |
| 5. 往来账款逾期 | 当前日期 > 账单到期日 due_date，且账单仍未结清 | 企业应收现金流受阻，账龄拉长导致呆账风险递增。 | 触发财务账龄催收通知，扣减业务员当期提成考核。 |
| 6. 售价底线异常 | 销售成交单价低于设定的最低指导售价 min_price | 销售利润被恶意侵蚀，价格体系崩溃引发窜货内讧。 | 审核时系统直接报错拦截，需总监级特批权限。 |


### 11.2 预警确认（warning_ack）管理闭环

系统不仅提供报警展示，更建立了严肃的预警知悉与消警闭环流程：

- 知悉确认留痕：管理人员在预警中心查看明细后，可针对特定预警项点击「确认知悉」。系统在 `warning_ack` 表中写入 `warning_key`、操作员 `created_by` 与当前时间戳，此预警在当前工作日不再频繁打扰推送。
- 自动消警闭环：当仓库实际完成补货、或财务实际收回应收款项使得指标恢复正常范围后，系统在下一次巡检时自动清除该预警记录，实现从预警产生、人为介入到业务消除的全生命周期自闭环。

## 十二、报表中心与经营分析模块深度设计


### 12.1 经营工作台核心 KPI 口径与公式定义

工作台首页展示的核心财务与经营指标定义严密，数据口径严格遵循会计电算化规范：

| 经营 KPI 指标 | 数学计算公式 | 数据统计源表 | 管理学意义与监控目标 |
| --- | --- | --- | --- |
| 1. 净销售额 (Net Sales) | 销售出库单总额 - 销售退货单总额 | documents (kind=sales_delivery/return, status=approved) | 衡量当期真实有效主营业务销售规模，剔除退货虚增。 |
| 2. 待收客户款 (Receivables) | SUM(bills.amount - bills.settled) [side='ar', state='active'] | bills (side='ar', state='active') | 反映企业目前沉淀在客户手中的待回笼流动资金规模。 |
| 3. 库存总资产 (Inventory) | SUM(inventory.quantity * inventory.value / quantity) | inventory (quantity > 0) | 反映当前所有仓库现有商品的物理账面结存资产总值。 |
| 4. 销售毛利润 (Gross Profit) | 净销售额 - 销售商品出库总成本 (cost) | documents & document_items | 企业核心盈利能力指标，出库成本精确结转扣减。 |
| 5. 资金回款率 (Collection Rate) | (当期客户净收款总额 / 当期净销售额) * 100% | settlements / documents | 衡量企业销售转化为现金流的效率，防范虚假繁荣。 |
| 6. 库存周转率 (Turnover Rate) | 当期销售出库总成本 / 期初期末平均库存资产 | document_items / inventory | 反映企业存货的流动性与运营周转效能，越高越健康。 |


### 12.2 核心业务报表矩阵

报表中心提供穿透至原始单据明细的多维交叉分析能力：

- 采购与销售趋势报表：按日、周、月维度聚合展示采购进货额、销售出库额、退货额与毛利走势，辅助管理层判断季节性周期波动。
- 商品排行分析报表：Top 20 热销商品排行（按销售额、销量、贡献毛利排序），精准识别“明星商品”与“亏损商品”。
- 往来单位贡献报表：核心大客户采购额与回款排行、主力供应商供货比重排行，为商务谈判与账期优惠提供精准数据背书。
- 业务员业绩报表：统计各业务员的名下开单额、实际回款额、退货率与毛利创收，为提成核算与绩效考核提供客观凭证。
- 进销存台账明细表：按“期初结存 + 本期入库 - 本期出库 = 期末结存”标准会计平衡恒等式，按商品和仓库逐笔展开变动流水，供审计与年终盘点对账。

### 12.3 报表聚合计算模型与索引优化策略

为确保在海量历史单据（数十万至数百万行）下报表依然实现秒级响应，系统在数据库层实施了针对性的组合索引覆盖：

- `idx_docs_filter` ON documents(kind, status, date)：覆盖单据类型、审核状态与日期的组合查询，极大加速工作台与月报的时间切片统计。
- `idx_bills_party` ON bills(side, partner_id, state, due_date)：覆盖往来账单的多条件状态过滤与到期日账龄切片，保证账龄表瞬间完成百万级账单聚合。
- `idx_inv_tx_doc` & `idx_inv_tx_inv` ON inventory_transactions：覆盖库存流水追溯查询，保障进销存台账按时间回溯重算时避免全表扫描。

## 十三、系统权限、安全管理与审计日志深度设计


### 13.1 增强型 RBAC 角色与权限体系架构

系统在 `users` 表与 `roles` 表中构建了细粒度、多层次的访问控制模型：

- 模块与操作级权限（permissions）：支持通配符 `*`（超级管理员所有权限）以及细分到具体模块的树状权限标识符。例如：`dashboard:view`（查看工作台）、`masters:product:edit`（修改商品）、`purchase:order:approve`（审核采购订单）、`finance:writeoff`（核销应收应付）、`reports:cost:view`（查看敏感成本价与毛利）。
- 数据可见性范围隔离（data_scope）：支持 `data_scope` 属性配置。若设为 `all`，用户可查阅全公司所有业务员的单据；若设为 `self`，用户仅能查看与操作自己（created_by = 当前用户 ID）开具的业务单据，实现销售员之间的客户与单据严密互斥隔离。
- 仓储实体权限约束（warehouse_ids）：支持在角色中绑定其有权访问的仓库白名单 ID 列表（JSON 格式）。仓管员仅能在其被授权的仓库内进行出入库与盘点操作，防止跨仓库越权发货。
- 敏感财务成本脱敏：针对商品采购单价、库存结存单位成本、销售单笔毛利率等机密财务指标，施加专门的字段级脱敏保护。未被授予财务权限的操作员在浏览单据与报表时，成本与毛利字段以 `***` 掩码呈现，彻底杜绝商业机密外泄。

### 13.2 接口幂等控制引擎（Idempotency Engine）

在网络抖动或客户端频繁快速点击场景下，极易发生“重复扣减库存”、“重复核销应收款”或“重复生成单据”的严重隐患。系统在 `idempotency` 表中建立了服务端幂等性保护机制：

```text
+------------------+                    +------------------+
    |   前端客户端     |                    |   后端 Gin 引擎  |
    +------------------+                    +------------------+
             |                                       |
             |  1. POST 请求携带 Header             |
             |     Idempotency-Key: <UUID>           |
             | ------------------------------------> |
             |                                       | 2. 查询 idempotency 表:
             |                                       |    SELECT * FROM idempotency 
             |                                       |    WHERE user_id=? AND key=?
             |                                       |
             |                                       +---------------+
             |                                       | 检查是否已处理|
             |                                       +---------------+
             |                                       |
             |  3. [情况 A: 已存在记录]             |
             |     直接返回已缓存的响应 JSON         |
             | <------------------------------------ | (不再执行任何业务事务)
             |                                       |
             |                                       | 4. [情况 B: 首次处理]
             |                                       |    开启业务事务执行开单/审核;
             |                                       |    保存执行结果至 idempotency 表;
             |  5. 返回执行成功响应                  |
             | <------------------------------------ |
```


### 13.3 操作审计日志（operation_log）与安全留痕

系统在底层通过统一审计函数 `audit(q, user, ip, action, entity, entity_id, before, after)` 实施全生命周期操作审计：

- 审计要素覆盖：操作人 ID（user_id）、用户名（username）、客户端真实 IP 地址（ip）、操作类型（action，如 create, update, approve, reverse, delete）、业务实体类型（entity，如 document, base_record, price_rule）、实体 ID、变更前数据快照（before_data JSON）、变更后数据快照（after_data JSON）、发生时间戳（created_at）。
- 不可篡改性保障：审计流水独立只读追加写入，严禁任何业务接口提供修改或物理删除操作日志的逻辑，确保系统具备金融级的反舞弊与事后法务举证追溯能力。

## 十五、单据生命周期与通用状态机流转设计


### 15.1 统一单据状态机跃迁图谱

所有核心进销存单据（采购单、销售单、入库单、出库单、调拨单、盘点单等）均受统一定义的严格状态机驱动：

```text
+-------------------+
                |   草稿 (Draft)    | <-----------+ (驳回退回)
                +-------------------+             |
                          | (提交审核)            |
                          v                       |
                +-------------------+             |
                |  待审核 (Pending) | ------------+
                +-------------------+
                          | (审核入账 - BEGIN IMMEDIATE)
                          v
                +-------------------+
                |  已审核 (Approved)| ----------------------------+ (全部执行完毕)
                +-------------------+                             |
                          | (部分下游执行, 如部分到货)             |
                          v                                       v
                +-------------------+                   +-------------------+
                | 执行中 (InProgress)| ----------------> |  已完成 (Completed)|
                +-------------------+ (完成全部执行)    +-------------------+
                          |
                          | (受控纠错流程)
                          v
                +-------------------+
                | 已作废 / 已冲销   |
                | (Voided/Reversed) |
                +-------------------+
```


### 15.2 状态跃迁控制与操作权限矩阵

| 当前初始状态 | 允许执行动作 | 跃迁后目标状态 | 前置业务校验条件与系统行为 |
| --- | --- | --- | --- |
| 草稿 (draft) | 保存/修改 | draft | 允许修改单据头与明细行，校验必填项与基本格式。 |
| 草稿 (draft) | 提交审核 | pending | 校验单据行项非空、单价与数量有效，锁定草稿编辑。 |
| 待审核 (pending) | 撤回/驳回 | draft | 将单据退回为草稿状态，恢复操作员修改权限。 |
| 待审核 (pending) | 审核通过 | approved | 开启原子事务：校验可用库存、重算移动平均成本、锁定预占或扣减库存、生成往来账单、记录审计流水。 |
| 已审核 (approved) | 部分下推 | in_progress | 当下游单据（如出库单）仅引用并执行了部分数量时自动跃迁。 |
| 已审核 (approved) | 反审核 (撤回) | draft | 严格校验：若下游已产生出库、入库或资金核销，强行阻断！仅在下游未动时回滚所有影响。 |
| 执行中/已审核 | 全额完成 | completed | 下游单据累计执行量达到 100%，上游订单自动归档闭环。 |
| 任何未结状态 | 作废/关闭 | voided | 释放销售订单预占库存，关闭单据后续流转。 |


### 15.3 乐观并发锁（Optimistic Locking）保障机制

在多操作员并发修改同一张单据时，为杜绝后提交的操作无声覆盖先提交的修改，系统在 `documents` 表中引入 `revision` 乐观锁机制：

- 版本号传递：前端获取单据详情时，必须一并读取当前的 `revision` 版本数值（如 revision = 3）；
- 原子递增：提交更新时，后端执行条件更新语句：`UPDATE documents SET ..., revision = revision + 1 WHERE id = ? AND revision = ?`；
- 冲突熔断：若影响行数 RowsAffected 等于 0，说明该单据在被当前用户编辑期间已被其他同事修改并保存。系统立即回滚事务并返回 `409 CONFLICT: 单据已被他人修改，请刷新最新版本后重试`，彻底阻断脏数据覆盖。

## 十六、数据安全、自动快照与灾难恢复引擎设计


### 16.1 SQLite 在线一致性快照技术（VACUUM INTO）

对于正在高频读写的数据库，传统的直接复制文件（File Copy）会导致严重的脏读、数据截断以及 WAL 日志不匹配引起的数据库损坏。系统彻底摒弃文件级拷贝，采用 SQLite 原生提供的在线一致性原子快照引擎：

- 在线原子快照：系统在后台执行 `VACUUM main INTO '<backup_file_path>'` 指令。该指令在数据库底层开启事务级只读一致性视图，将全部有效数据页紧凑整理并原子写入独立的备份物理文件中，整个过程不阻塞前端正常查询与业务录入。
- 快照自检与验真：快照生成后，系统立即为备份文件计算 SHA-256 摘要哈希值，并在独立的只读连接中执行 `PRAGMA integrity_check` 与外键约束检查。只有自检 100% 通过的副本才会被标记为「可用快照」并计入 `backup_records` 表。

### 16.2 多梯度备份保留策略（Retention Policy）

系统内置高密度的自动化定时备份守护协程，执行多梯度的保留归档策略：

| 备份梯队 | 执行频次与触发时机 | 保留副本数量 | 灾难防护目标 |
| --- | --- | --- | --- |
| 高频运行快照 | 系统运行期间每 15 分钟自动执行一次 | 保留最近 192 份（覆盖 48 小时） | 应对突发断电、操作员严重误操作或数据误覆盖，实现超低 RPO（<=15分钟）。 |
| 每日归档基线 | 每日深夜业务低谷期自动归档一份全量基线 | 保留最近 14 份（覆盖 14 天） | 支撑半个月内的按天级完整历史状态回溯与财务对账。 |
| 周度历史快照 | 每周日深夜执行周度归档并压缩 | 保留最近 12 份（覆盖一季度 3 个月） | 支撑季度财务审计与阶段性经营成果归档。 |

### 16.3 客户端原生一键灾难恢复协议

当遭遇硬盘逻辑坏道、勒索病毒攻击或极端人为误删时，系统在桌面客户端与 Web 运维中枢提供了一键式恢复协议：

```text
+-----------------------------------------------------------------------------------+
    |                              客户端原生灾难恢复协议流程                           |
    +-----------------------------------------------------------------------------------+
    1. 操作员在客户端界面选择目标备份快照，输入超级管理员密码进行二次强鉴权;
    2. 系统安全停止当前正在运行的 Go 后端服务，并获取数据目录的排他独占文件锁 (File Lock);
    3. [自保机制] 将当前故障数据库 (ruilian.db, -wal, -shm) 完整拷贝至 pre_restore_backup 目录，
       确保即使恢复失败也能保全现场;
    4. 执行物理替换：将目标快照解压并原子重命名覆盖当前的 ruilian.db 文件，并清理陈旧 WAL/SHM;
    5. 重新载入底层数据库，执行 PRAGMA quick_check 验证物理结构完好性;
    6. 重新校验安装记录与授权状态 (system_installation & license_local);
    7. 恢复完成，向 operation_log 写入灾难恢复审计日志，客户端自动平滑重载回到工作台。
    +-----------------------------------------------------------------------------------+
```


## 十七、软件授权与防破解安全体系设计


### 17.1 双模态授权架构设计

为满足商业化推广与客户私有化交付诉求，系统在底层构建了标准化的双模态授权流转体系：

- 1. 10 天免费安全试用模式（Trial Mode）：系统在首次初始化安装时，在 `system_installation` 表中记录初始运行时间戳，自动开启 10 天（10×24 = 240 小时）的全功能无限制试用。登录页与系统顶部常驻试用倒计时横幅（TrialBanner），提醒用户剩余天数并提供一键授权入口。
- 2. 永久商业授权模式（Permanent Mode）：客户向软件发行方购买商业授权后，发行方使用独立的授权生成工具（licensegen）签署并下发激活凭证。客户在系统后台导入激活码后，系统激活为永久商业授权状态，顶部试用条自动消失。

### 17.2 机器硬件指纹绑定（Installation ID）

为防范激活码被客户在多台未授权计算机上随意复制盗用，系统在客户端采集硬件特征生成唯一且不可逆的设备指纹：

- 硬件特征采集项：主板序列号（Motherboard UUID） + CPU 唯一处理器序列号 + 主网卡 MAC 地址硬件特征。
- 不可伪造指纹：通过 SHA-256 慢哈希进行多次不可逆散列运算，生成标准 32 位机器安装标识符（如 `RL-8F2A-9C3D-E451-B206`），存入 `system_installation.installation_id`。

### 17.3 Ed25519 非对称数字签名与私钥绝对物理隔离

传统的对称加密（如 AES/DES）需要将解密密钥编译在客户端中，极易被逆向工程逆向提取。睿链在架构上实施严格的非对称现代密码学体系：

```text
+----------------------------------------+        +----------------------------------------+
    |       发行方环境 (Publisher Only)      |        |        客户运行环境 (Client App)       |
    |      [完全物理隔离，绝不进入代码库]    |        |                                        |
    +----------------------------------------+        +----------------------------------------+
                        |                                                  |
     1. 生成 256 位 Ed25519 私钥/公钥对;                                   |
        - 私钥: 存放于发行方离线高密保险箱;                                |
        - 公钥: 硬编码内嵌于客户端 LicenseService; ------------------------>+ [内置验签公钥]
                        |                                                  |
     2. 发行方授权工具 (licensegen) 组装 Payload:                          |
        {                                                                  |
           "customer": "北京某商贸有限公司",                                |
           "installation_id": "RL-8F2A-...",                              |
           "product": "RUILIAN_ERP",                                       |
           "version_range": "1.0~2.0",                                     |
           "expire_at": "9999-12-31"                                       |
        }                                                                  |
                        |                                                  |
     3. 使用离线私钥对 Payload 进行 Ed25519 数字签名:                      |
        Signature = Ed25519Sign(PrivateKey, Payload)                       |
                        |                                                  |
     4. 生成授权许可证文件 / 激活码字符串                                   |
                        |                                                  |
                        +---------------- 发送给客户 --------------------->+
                                                                           |
                                                     5. 客户端执行非对称验签:
                                                        Valid = Ed25519Verify(PublicKey, Payload, Sig)
                                                        IF Valid && Payload.installation_id == LocalID:
                                                            激活成功！写入 license_local 表;
```


### 17.4 防系统时间恶意篡改与倒退攻击（Anti-Clock Tampering）

试用期软件极易遭受恶意用户通过“将计算机系统时钟调回过去”来无限延长试用期。系统设计了单向递增防篡改封印机制：

- 运行时间水印：系统在每次运行时，以 UTC 时间戳更新 `system_installation.last_run`，并结合内部混淆盐值计算 HMAC-SHA256 签名（seal 字段）。
- 倒退熔断拦截：每次系统启动或执行核心写操作时，校验当前系统时间 $T_{now}$ 是否小于记录的 $T_{last}$。若发现时钟倒退超过 60 秒的合理误差容限，系统立即判定为恶意篡改攻击，锁定系统并在 `license_event_log` 中记录篡改报警，阻断试用期倒退。

### 17.5 授权到期降级安全底线

当试用期届满（> 10 天）且用户未输入合法激活码时，系统恪守商业软件的安全伦理底线：

> 【商业授权伦理与安全底线】
> 授权到期行为规范：
> 1. 写操作全面拦截：严格拦截所有新增采购、入库、销售、出库、调拨、收付款等非幂等写操作，提示「试用期已结束，请购买正版授权」；
> 2. 数据资产永不扣押：系统永久保留客户已有历史数据的只读查询、历史单据查看、财务报表导出为 Excel 以及完整数据库一键备份功能；
> 3. 绝对禁止以任何形式损坏、格式化或恶意加密客户已有经营数据。


## 十八、SaaS 多租户物理隔离架构与超级管理员中枢设计


### 18.1 Database-per-Tenant 物理数据库独立架构

在集团多组织与 SaaS 云化架构下，传统的「共享库表、以 tenant_id 字段过滤」的逻辑隔离方案存在巨大的安全隐患——一旦研发人员在某处手写 SQL 遗漏了 `WHERE tenant_id = ?`，将直接导致不可挽回的跨企业数据穿透与商业机密泄漏。系统坚决推行 Database-per-Tenant 物理级强隔离架构：

```text
data/
    |-- ruilian.db                 # [平台主管理库] 仅超级管理员 huxinkui 与全局总控使用
    |-- ruilian.db-wal             # 主管理库预写日志 (WAL 模式)
    |-- ruilian.db-shm             # 主管理库共享内存
    |-- backups/                   # 全局与主空间备份归档目录
    |-- logs/                      # 系统运行日志与安全审计日志
    `-- tenants/                   # [租户独立沙箱根目录]
        |-- xuyonghong/            # 租户专属物理目录 (以唯一租户代码 tenant_code 命名)
        |   |-- ruilian.db         # 该租户专属的独立 SQLite 物理数据库
        |   |-- ruilian.db-wal     # 租户独立 WAL 日志文件
        |   `-- ruilian.db-shm     # 租户独立共享内存文件
        |-- corp_bj/               # 分支机构 A 独立沙箱
        |   `-- ruilian.db
        `-- corp_sh/               # 分支机构 B 独立沙箱
            `-- ruilian.db
```


### 18.2 动态租户路由中间件（Tenant Routing Middleware）

系统在后端通过 `TenantManager` 维护租户 `App` 实例的动态缓存池，实现零感知动态请求分发：

- 多通道识别：分发规则按优先级识别：HTTP Header `X-Tenant-Code` > Cookie `ruilian_tenant` > URL Query 参数 `?tenant=xxx`。若未指定或为 default，则分发至平台主空间。
- 并发安全实例池：TenantManager 内部采用读写锁（sync.RWMutex）保护 App 实例池。当首次请求某个租户时，按需懒加载并初始化该租户的独立物理数据库连接池，保证高并发线程安全。

### 18.3 物理存储配额与写操作拦截引擎（Storage Quota Engine）

在多租户平台环境下，单个租户的恶意写入或数据急剧膨胀极易耗尽服务器整机磁盘，拖垮其他正常企业。系统在底层实现毫秒级物理穿透统计与写拦截：

- 配额定义：租户注册主表中定义 `max_storage_mb` 字段（支持 200MB、500MB、1GB、2GB 或 0 不限容量）。
- 穿透统计：系统通过 `GetTenantStorageUsage` 穿透物理文件系统，递归累加租户沙箱目录下主库、WAL 日志、SHM 共享内存及日志文件的真实物理字节总和。
- 毫秒级写拦截：在所有非幂等写操作（POST, PUT, DELETE, PATCH）到达业务层之前，中间件执行 `CheckStorageQuota`。一旦发现实际占用 >= 配额上限，即刻阻断请求并返回 `403 STORAGE_QUOTA_EXCEEDED`，同时将租户降级为只读模式，有力保护宿主机硬件安全。

### 18.4 默认管理员账号注销与超级管理员专属化（huxinkui）

针对公网与局域网长期遭受针对通用用户名（admin/administrator）的大规模自动化爬虫扫描与暴力破解风险，系统在 V1.2 中实施了坚决的安全重构：

| 安全维度 | 旧版机制 (V1.0/V1.1) | 新版架构标准 (V1.2) | 安全提升与防御价值 |
| --- | --- | --- | --- |
| 超级管理员用户名 | 默认通用 admin | 专属安全标识 huxinkui | 彻底抹平互联网扫描工具与弱密码字典的探测入口。 |
| 默认 admin 账号行为 | 允许登录，弱口令高危 | 全面注销废弃，登录一律直接报错阻断 | 消除默认账户暴露面，杜绝撞库扫描风险。 |
| 租户空间账号规范 | 租户库中曾残留 admin | 强制清退，严禁 admin/huxinkui 存在 | 各租户仅保留与其代码同名的管理员（如 xuyonghong）。 |
| 防暴力破解机制 | 仅依赖基础单向哈希 | IPLoginLimiter 针对 IP 频次统计封禁 | 单 IP 连续失败 8 次自动封禁 15 分钟，阻断自动化脚本。 |
| 图形安全验证码 | 无验证码 | CaptchaStore 字符随机扰动与干扰线 | 内存单次消费机制，抵御 OCR 识别与接口自动化撞库。 |


### 18.5 权限边界与多租户管理中枢强隔离

为保证普通租户专注于自身业务，严防垂直越权与横向越权，系统构筑了前后端一体的双重防护城墙：

- 前端界面完全隐形：普通租户登录后，侧边栏导航自动剔除「多租户管理」菜单项；顶部多租户切换器对租户完全不渲染，租户感知不到平台其他企业的存在。
- 前端路由全天候强守卫：Vue Router 全局前置守卫拦截对 `/tenants` 的一切访问，一旦识别非超级管理员身份，立即弹出警告通知并重定向回业务首页。
- 后端 API 强鉴权中间件：后端 `/api/system/tenants` 接口全量挂载 `requireMasterAdmin` 中间件，强制校验 `(u.IsMasterAdmin || u.Username == 'huxinkui') && a.TenantCode == 'default'`。租户尝试直连请求一律返回 `403 Forbidden`，彻底杜绝越权操作。

### 18.6 超级管理员专属平台总控运维控制台（Admin Dashboard）

系统在前端为不同身份提供了清晰的「视界分离」体验：

- 超级管理员视界（Admin Dashboard）：展示平台运维 Hero 中枢、超级管理员专属标识、实时脉冲健康呼吸灯、四维运维 KPI 网格（租户总数、物理存储占用、容量预警租户、核心防御在线状态）、ECharts 租户物理体积占用比例饼环图。
- 租户空间管控舰队：呈现完整的租户空间管控舰队（Tenant Fleet）。支持按租户代码、名称搜索与状态过滤；以动态颜色进度条透视物理存储占用与路径（`data/tenants/{code}/ruilian.db`）；提供一键跨空间巡检、动态调整配额、重置租户管理员密码、启停租户状态等运维操作。
- 跨空间监管巡检联动：超级管理员在总控台点击「跨空间巡检」后，无缝进入任意子租户的业务系统，页面顶部常驻红色监管横幅：“`跨租户监管中: <租户名> [代码]`”并附带“`返回平台总控台`”按钮，实现跨空间监管与平台中枢的顺畅穿透与回跳。

## 十九、现有架构深度评估与技术瓶颈诊断


### 19.1 当前单体 + SQLite 物理隔离架构的优劣势客观评估

在对架构进行未来优化升级之前，必须客观、全面地审视系统当前 V1.2 架构的综合表现：

| 核心维度 | 架构现状表现 | 优势与工程收益 | 局限性与潜在瓶颈 |
| --- | --- | --- | --- |
| 部署与交付 | 单体二进制 + 纯 Go SQLite，无外部依赖 | 零安装配置、极低内存占用（<50MB）、极速冷启动、一键打包为桌面客户端。 | 仅适用于单机或集中式单节点部署，无法直接在无状态容器集群中做多副本水平伸缩。 |
| 多租户隔离 | Database-per-Tenant 物理数据库独立沙箱 | 数据物理级隔离，连接池与事务锁完全独立，杜绝 SQL 漏写租户 ID 造成的穿透泄露。 | 租户数量达到数万级时，海量 SQLite 数据库文件句柄（FD）管理与动态加载面临系统开销。 |
| 单节点读性能 | WAL 预写日志模式，纯内存读 | 读写互不阻塞，单租户内部毫秒级响应，单机读取吞吐量极佳。 | 受限于宿主机单节点物理磁盘 I/O 上限，无法进行跨多物理服务器的分片扩展。 |
| 单节点写并发 | SQLite 原生排他写锁（BEGIN IMMEDIATE） | 强一致性事务保护，严防脏读、幻读与超卖，开发复杂度低、可靠性极高。 | 单租户数据库同一时刻仅允许一个并发写事务，在高并发抢购或大批量导入时存在写排队等待。 |
| 全局报表分析 | 各租户物理数据库完全独立 | 各租户历史单据分析互不影响，单个租户的大型报表计算绝不拖慢其他企业。 | 平台管理层若需统计全局租户的跨库汇总大盘，需逐个遍历所有物理文件，聚合开销显著。 |


### 19.2 核心性能瓶颈与扩展性瓶颈诊断

- 1. 单写锁排他性吞吐瓶颈：在高并发开单场景下，多个操作员同时提交出库单时，SQLite 写锁会导致排队等待。当写事务耗时较长（如复杂的移动平均成本重算或大规模批量入库）时，可能触发 `database is locked` 错误（虽然系统设置了 busy_timeout，但依然会增加请求等待时延）。
- 2. 缓存体系缺失与频繁 I/O：单体架构中缺少分布式缓存（如 Redis），对于高频读取的商品主档、价格阶梯规则以及用户 Session，每次请求均需穿透到数据库，增加了磁盘 I/O 负担。
- 3. 同步重型链路缺乏削峰解耦：单据审核后的库存记账、成本结转、应收账款生成、预警计算与操作审计均为同步串行执行。一旦链路中某一环节变慢，整个 HTTP 响应时间随之拉长，亟需引入异步消息解耦机制。
- 4. 复杂 OLAP 报表与 OLTP 交易读写混杂：当企业单据明细累积至千万级时，基于关系型数据库的复杂多维统计（如跨年度销售毛利环比、商品与客户交叉分析）会导致全表扫描或大索引合并，影响常规业务开单性能。

### 20.2 存储层双引擎解耦方案（Dual-Engine Storage Adapter）

为兼顾「本地单机/边缘端轻量级免运维交付」与「云端多租户超高并发弹性伸缩」，系统重构数据访问层，抽象出统一的 Storage Adapter：

```text
// Go 统一存储访问接口抽象
    type StorageAdapter interface {
        GetDB(ctx context.Context, tenantCode string) (*sqlx.DB, error)
        ExecuteTransaction(ctx context.Context, tenantCode string, fn func(tx *sqlx.Tx) error) error
        GetDialect() DialectType // DialectSQLite, DialectPostgres, DialectMySQL, DialectTiDB
    }
```

- 模式 1：本地边缘轻量版（SQLite Adapter）：在桌面安装包、单店单机或边缘端设备上，系统自动装载 SQLite 物理沙箱适配器。无需安装任何数据库服务，零配置即开即用，保持极致的轻量与便携特性。
- 模式 2：企业级云端集群版（PostgreSQL / TiDB Adapter）：在云端 SaaS 或大型集团私有云部署中，系统一键切换至 PostgreSQL / TiDB 适配器。底层全面支持连接池自动伸缩、行级读写锁（SELECT ... FOR UPDATE）、读写分离，彻底打破 SQLite 单写锁吞吐量瓶颈，支撑单租户数千 TPS 的并发开单需求。
- 混合多租户模式演进：在云端版中，系统提供阶梯租户隔离模式：针对核心战略大客户提供 Database-per-Tenant 独立物理分库；针对中小型租户提供 Schema-per-Tenant（逻辑隔离加命名空间物理边界）模式，在隔离安全性与服务器硬件成本之间实现最佳商业平衡。

### 20.3 领域驱动设计（DDD）与模块化单体解耦

系统按照领域驱动设计（Domain-Driven Design）规范对业务代码进行深度重构，划定清晰的限界上下文（Bounded Context）：

| 业务限界上下文 | 核心聚合根 (Aggregate Root) | 领域实体与值对象 | 对外暴露领域事件 (Domain Events) |
| --- | --- | --- | --- |
| 基础主档域 (Master) | Product, Partner, Warehouse | Category, Unit, Spec, Location | ProductCreated, PartnerCreditChanged |
| 交易履约域 (Trade) | PurchaseOrder, SalesOrder | DocumentItem, PriceSource | OrderApproved, OrderCancelled, OrderCompleted |
| 仓储库存域 (Inventory) | Inventory, StockTransfer | InventoryTransaction, Batch, Serial | StockDeducted, StockReplenished, CostRecalculated |
| 往来资金域 (Finance) | Bill, Settlement | Writeoff, BillOffset, CreditLimit | PaymentReceived, BillSettled, CreditOverdrawn |
| 价格策略域 (Pricing) | PriceRule | CustomerTierPrice, Promotion | PriceRuleActivated, PriceRuleExpired |
| 租户管控域 (Tenant) | Tenant, SystemQuota | StorageUsage, UserAudit, Seal | TenantCreated, QuotaExceeded, TenantStatusChanged |

各领域遵循整洁架构（Clean Architecture）原则，领域层不依赖具体数据库技术或外部 HTTP 框架，领域之间严格通过定义明确的领域事件（Domain Events）与应用服务契约通信。系统既能以「高性能模块化单体」高效运行，也能在未来按需平滑拆分为微服务独立部署。


### 20.4 分布式缓存与并发控制升级（Redis & Redlock）

为应对高并发场景下的数据读取与库存并发扣减，系统构建多级缓存与分布式锁机制：

- 两级缓存架构：本地一级缓存（In-Process BigCache/GoCache，毫秒级以下无锁读取） + 集中二级缓存（Redis Cluster）。对高频读取的商品主档、字典分类、价格阶梯规则进行全量缓存；在主档发生变更时，通过 Redis Pub/Sub 广播失效本地缓存，兼顾超高吞吐与数据一致性。
- Redlock 分布式锁保障：在秒杀或大促批量开单场景下，多个并发请求同时争抢同一商品的可用库存。系统引入基于 Redis 的 Redlock 分布式锁，加锁粒度细化至 `lock:inventory:{tenant}:{product_id}:{warehouse_id}`。请求在分布式锁保护下原子执行库存校验与预占扣减，杜绝并发超卖。

### 20.5 异步消息驱动与事件总线（Event-Driven Architecture）

单据审核是一项重型业务操作，涉及库存扣减、加权成本重算、往来账单生成、预警扫描与审计留痕。系统通过引入 Apache Kafka / RabbitMQ 消息总线，实施事务出站模式（Transactional Outbox Pattern）：

```text
+-----------------------------------------------------------------------------------+
    |                              事务出站模式 (Transactional Outbox)                   |
    +-----------------------------------------------------------------------------------+
    1. 用户点击「审核销售出库单」;
    2. 后端开启数据库本地事务 BEGIN:
       - 更新单据状态 documents.status = 'approved';
       - 扣减库存与释放预占 inventory.quantity -= qty, reserved -= qty;
       - 在 outbox_events 本地事件表中插入事件: 
         { "event": "SalesDeliveryApproved", "doc_id": 1002, "payload": {...} };
    3. 提交本地事务 COMMIT; (此时关键库存与单据已被强一致提交)
    4. 立即向前端返回 HTTP 200「审核成功」; (耗时缩短至 < 20ms)
    5. 独立消息中继器 (Message Relay) 监听 outbox 表，将事件可靠投递至 Kafka / RabbitMQ;
    6. 异步消费者集群并发执行下游任务:
       - 消费者 A: 计算移动加权平均成本流水与结转毛利;
       - 消费者 B: 在 bills 表生成客户应收账单并触发自动核销;
       - 消费者 C: 刷新客户风险敞口与预警雷达;
       - 消费者 D: 发送企业微信/钉钉/邮件开单通知，并触发第三方 Webhook.
    +-----------------------------------------------------------------------------------+
```


### 20.6 CQRS 读写分离与千万级大数据报表引擎

面对海量历史数据下的复杂分析报表，传统的 OLTP 数据库难以抗衡。系统全面推行 CQRS（命令与查询职责分离）架构：

- 交易写模型（Command OLTP）：交易写库专注于高速单据录入、库存锁库与资金对账，严格遵循第三范式，保障 ACID 事务强一致性与超低写入时延。
- 报表读模型（Query OLAP）：通过 Debezium / Flink CDC 实时捕获交易库的二进制变更日志（Binlog / WAL），流式同步至列式数据库 ClickHouse 与搜索引擎 ElasticSearch，构建面向分析的宽表与多维聚合立方体（Data Cube）。
- 性能百倍提升：管理层查询跨年度进销存大盘、商品销售排行榜、账龄结构分析等报表时，直接由 ClickHouse 提供秒级甚至毫秒级响应，即使面对千万级明细流水亦能瞬间出图，且完全不消耗交易写库的 CPU 与内存资源。

### 20.7 零信任安全框架与企业级身份认证

系统在安全体系上全面迈向企业级零信任（Zero Trust）架构：

- 统一企业 SSO：引入基于 OAuth 2.0 / OIDC 标准的统一身份认证，支持打通企业微信、飞书、钉钉、微软 Active Directory 及企业现有 LDAP 服务，实现员工一键安全免密单点登录（SSO）。
- 无感令牌轮转机制：采用动态双令牌机制：15 分钟短效 Access Token + 7 天长效 Refresh Token。每次刷新时自动轮转 Refresh Token（Token Rotation），一旦检测到旧 Token 重放立即冻结会话，杜绝 Token 窃取风险。
- 敏感数据透明列级加密：对数据库中存储的客户真实手机号、银行账户、采购底价等高敏感字段实施列级透明硬件加密（AES-256-GCM），配合可信密钥管理服务（KMS），防止数据库物理文件泄漏引发合规灾难。

### 20.8 云原生高可用容灾与自动化运维

- Kubernetes 编排：前后端全面容器化，提供开箱即用的 Dockerfile 与 Kubernetes Helm Chart 配置。支持在阿里云 ACK、腾讯云 TKE 或私有 K8s 集群上一键自动化部署。
- 弹性伸缩（HPA）：应用层无状态设计，基于 K8s HPA（Horizontal Pod Autoscaler）根据 CPU 占用率与请求 QPS 自动在秒级弹性扩缩容 Pod 副本数，轻松应对业务高峰与低谷。
- 跨机房多活与异地容灾：生产环境采用跨可用区（Multi-AZ）多机房容灾部署。数据库主备实例秒级自动心跳与故障切换，备份文件通过加密通道自动跨地域异步同步至云对象存储（如阿里云 OSS、腾讯云 COS、AWS S3），保障企业数据资产坚如磐石。

### 20.9 开放平台与生态互联（OpenAPI 3.0）

为使睿链无缝融入企业上下游数字化生态，系统规划企业级开放平台（OpenAPI Platform）：

- 标准化开放网关：基于 OpenAPI 3.0 标准提供统一 RESTful API 网关，覆盖基础资料同步、单据下推、库存查询与资金对账。
- 企业级安全签名鉴权：为各租户颁发专属 `AppKey` 与 `AppSecret`，API 调用采用 `HMAC-SHA256` 签名算法，配合随机 Nonce 与时间戳防止重放攻击。
- 标准 Webhook 回调体系：支持单据审核、库存变更、客户信用告警等事件的标准 Webhook 订阅推送，外部系统可配置回调 URL 实时接收业务消息。
- 主流生态连接器与 SDK：提供官方 Go、Java、Python、Node.js 客户端 SDK；预置对接主流电商平台（淘宝、京东、抖音电商）、智能 POS 硬件及用友/金蝶财务软件凭证导入导出的标准连接器（Connectors）。
