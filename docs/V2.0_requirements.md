一、 软件总体架构定位与核心设计目标

「睿链进销存与往来管理系统」（RUILIAN ERP）定位于企业级采购、销售、库存及往来账务一体化管理平台。针对集团化多组织管控与 SaaS 云端多租户托管需求，本架构设计在 V1.2 基础之上进行了全方位深度完善，重点强化了多租户物理隔离体系、平台超级管理员（huxinkui）专属总控与穿透巡检能力、空间配额精细化治理，并针对高并发与海量数据场景给出了完整的工程优化方案。

2.2 租户上下文路由与 Session 强绑定防越权机制

为彻底防范租户通过篡改 HTTP 请求头（如伪造 X-Tenant-Code）实现横向跨租户越权访问，系统在网关边界层构建了「双因子租户上下文校验管道」：

1. 多通道标识解析：请求租户标识提取优先级：HTTP Header (X-Tenant-Code) > 专属穿透令牌 (X-Impersonate-Token) > Cookie (ruilian_tenant) > URL Query (?tenant=xxx)。

2. 会话与租户空间强绑定（防横向越权核心）：任何普通租户用户在登录成功后，其生成的会话记录与 Token 载荷中强制硬编码绑定所属的 tenant_code。在后续业务 API 调用中，中间件强制比对 Token 绑定的 tenant_code 与当前路由解析的 tenant_code。一旦两者不一致且当前用户非超级管理员 huxinkui，系统立即判定为横向越权攻击，直接返回 HTTP 403 TENANT_CONTEXT_MISMATCH 并记录安全告警。

3. 路径穿越防御（Path Traversal Guard）：所有租户代号在拼接文件路径前，必须通过严格的白名单正则校验（仅允许小写字母、数字与下划线）并使用 filepath.Clean 与前缀校验，严防利用 ../ 等字符实施路径穿越读取宿主机敏感文件。

三、 专属超级管理员（huxinkui）权限体系与后台数据监管设计

3.1 默认管理员账号重构与 huxinkui 专属化硬边界

系统在底层初始化与安全鉴权引擎中，全面拔除传统的通用管理员标识（admin / administrator / root），确立 huxinkui 为平台唯一超级管理员账号：

1. 主库唯一初始化：系统首次启动初始化主库（data/ruilian.db）时，自动创建 username = 'huxinkui' 的主平台超级管理员账户，绑定全局最高权限角色（permissions = ['*']，is_master_admin = 1）。

3. 租户库账号命名空间净化：在所有子租户数据库（data/tenants/{code}/ruilian.db）的初始化与用户创建接口中，强制设置保留字黑名单，严禁在子租户内创建名为 huxinkui 或 admin 的账户。子租户默认管理员账号统一规范为其租户代码同名账号（即 {tenant_code}）。

四、 现有架构深度诊断与核心优化意见

基于现有 V1.2 架构设计说明书的深入审视，虽然当前系统已实现了基础的 Database-per-Tenant 隔离与定点计算闭环，但在高密度多租户运行、极端并发场景及系统长期运维层面，仍存在 6 个关键技术隐患。以下给出针对性的架构优化意见与工程落地改造方案：

4.1 优化意见一：引入基于 LRU + 空闲超时淘汰的动态连接池（解决文件句柄耗尽隐患）

【现状痛点诊断】：在现有 V1.2 架构中，TenantManager 采用按需懒加载初始化租户的 SQLite 连接池并常驻内存。当平台租户数量增长至数百或数千家时，每个活跃 SQLite 实例均会长期持有 3 个文件描述符（.db、.db-wal、.db-shm）。这极易触发操作系统最大打开文件句柄限制（ulimit -n，Too many open files）以及内存溢出。

【架构优化方案】：重构 TenantManager，引入「LRU（最近最少使用）+ Idle TTL（空闲超时回收）」双驱淘汰机制：

1. 设定平台最大并发活跃租户连接池上限（如 MaxActiveTenants = 128），并维护双向链表记录各租户最后访问时间戳；
2. 针对每个租户的 SQLite 连接池，严格区分「读写连接池（MaxOpenConns=1，配合 BEGIN IMMEDIATE 避免锁冲突）」与「只读连接池（MaxOpenConns=4，开启 query_only=1 并发读取）」；
3. 后台守护协程每 5 分钟扫描一次：凡是超过 15 分钟无任何 API 请求的静默租户，先自动执行一次 `PRAGMA wal_checkpoint(PASSIVE)` 将预写日志落盘，随后安全调用 `db.Close()` 释放文件句柄与内存；当下次该租户发起请求时，在 2ms 内无感透明重连。

4.2 优化意见二：存储配额引擎引入「内存原子计数 + 滞回防抖双水线」机制（消除高频磁盘 I/O 扫描）

【现状痛点诊断】：现有设计中，在每次写操作（POST/PUT/DELETE）前通过 `GetTenantStorageUsage` 递归遍历租户物理目录累加字节数。在高并发开单下，频繁调用操作系统 `os.Stat / filepath.Walk` 会造成严重的系统调用开销；且当容量处于临界值附近时，极易发生频繁的“封禁-恢复”震荡。

【架构优化方案】：采用「内存缓存 + 异步校准 + 滞回防抖（Hysteresis Watermark）」三重优化：

1. 内存原子感知：在 TenantInstance 结构体中维护 `atomic.Int64` 类型的 `usedBytes` 内存计数器，CheckStorageQuota 直接读取内存数值，耗时从毫秒级降至纳秒级（< 50ns），零磁盘 I/O 开销；
2. 触发式与周期式同步：每当该租户累计完成 50 次写事务，或每隔 60 秒由后台协程异步扫描一次物理文件目录（含 .db、-wal、-shm 及 backups），刷新内存计数器并同步至主库 `tenants.current_storage_bytes`；
3. 滞回防抖双水线设计：设定三级水线——① 软预警线（85% 配额）：正常写入，但在响应头返回 `X-Quota-Warning: 85%` 并在工作台提醒租户清理或扩容；② 硬熔断上限（100% 配额）：触发只读锁定（状态置为 `readonly_quota`），拦截业务新增写操作；③ 恢复解封下限（92% 配额）：一旦触发只读锁定，必须等管理员扩容或清理数据使占用率降至 92% 以下才自动解除锁定，彻底消除临界点状态高频抖动。

4.3 优化意见三：多租户 Schema 演进与自动化灰度迁移引擎（解决多库结构升级难题）

【现状痛点诊断】：Database-per-Tenant 架构最大的工程挑战在于版本升级：当软件从 V1.2 升级至 V2.0 需要新增表或字段时，如何安全、一致地更新成百上千个独立的 `ruilian.db` 文件？若启动时同步全量迁移，会导致系统启动极慢；若某租户库迁移失败，甚至会导致整个服务崩溃。

【架构优化方案】：构建「启动主库迁移 + 租户懒加载即时迁移（Lazy Migration）+ 后台批量巡检」机制：

1. 版本号水位管理：在主库 `tenants` 表与每个租户库的 ` PRAGMA user_version` 中双向记录当前 Schema 版本号；
2. 按需即时迁移（Lazy-On-Load）：当 TenantManager 加载某个租户数据库时，首先比对 `user_version` 与当前二进制代码的目标版本 `TargetSchemaVersion`。若版本落后，立即获取该租户独占锁，在执行迁移前自动执行一次 `VACUUM INTO` 备份，随后在事务内顺序执行增量 SQL 脚本，更新版本号后再放行请求；
3. 总控台一键升级监控：管理员 huxinkui 可在总控台直观看到所有租户的 `db_version` 分布，并支持在夜间低峰期发起后台批量静默升级。

4.4 优化意见四：分库架构下的跨租户后台数据聚合优化（推拉结合取代全量遍历）

【现状痛点诊断】：管理员 huxinkui 在查看所有租户的后台经营汇总与排行时，若实时遍历所有 `data/tenants/{code}/ruilian.db` 进行聚合查询，随着租户数量增加，接口响应时间将呈 O(N) 线性恶化。

【架构优化方案】：建立「事件旁路异步上报 + 主库摘要快照表」机制：

在每个租户发生核心写操作（如单据审核入账、收付款核销、新增商品）提交事务后，通过 Go 内存无阻塞 Channel 异步触发该租户的增量指标重算，并直接 Upsert 更新至主库 `data/ruilian.db` 的 `tenant_metrics_snapshot` 表中。管理员 huxinkui 打开总控后台时，100% 查询主库单表即可在 5ms 内获取全平台所有租户的实时经营数据、库存总值与应收账款大盘。

4.5 优化意见五：租户级防误锁与配额死锁逃生通道设计

【现状痛点诊断】：当某个租户因磁盘配额达到 100% 被 `StorageQuotaEngine` 拦截一切 POST/PUT/DELETE 请求时，如果连「删除无用草稿单据」、「清理历史旧快照」或「管理员重置配置」的请求也被一刀切拦截，将导致租户陷入无法自救的死锁状态。

【架构优化方案】：在 `CheckStorageQuota` 中间件中建立「逃生白名单路由（Quota Exempt Routes）」：

即使租户处于 `readonly_quota` 超限状态，系统依然放行以下减容与管理操作：① 超级管理员 huxinkui 发起的一切代维请求；② 用户退出登录接口（POST /api/auth/logout）；③ 删除草稿状态单据（DELETE /api/documents/:id）；④ 删除历史陈旧备份快照与执行数据库 `VACUUM` 压缩瘦身接口。

4.6 优化意见六：精细化备份调度器（错峰抖动防止磁盘 I/O 风暴）

【现状痛点诊断】：系统设计了每 15 分钟一次的高频快照（VACUUM INTO）。在多租户场景下，若 200 个租户在同一时刻（如整点 00 分、15 分）同时触发 `VACUUM INTO`，会导致宿主机瞬间产生巨大的磁盘写放大与 I/O 阻塞。

【架构优化方案】：引入「脏标记跳过（Dirty Flag Check）+ 哈希时间片错峰抖动（Consistent Hash Jitter）」：

1. 静默租户零备份：在 TenantManager 中记录每个租户的 `last_write_time` 与 `last_backup_time`。若自上次备份以来，该租户未发生任何写事务（无任何新单据或修改），直接跳过本次 15 分钟定时备份，避免生成大量完全重复的冗余快照；
2. 哈希错峰调度：对发生过数据变更的活跃租户，根据 `crc32(tenant_code) % 900`（900秒即15分钟）计算专属偏移秒数，将各租户的备份任务均匀打散在 15 分钟的时间窗内平滑执行。

五、 核心代码架构与关键中间件实现规范 (Go + Gin)

以下提供经完善优化后的核心后端架构代码实现蓝图，涵盖 `TenantManager` LRU 实例池、双重防越权路由中间件、`huxinkui` 专属鉴权与跨空间穿透守卫：

// 1. 核心数据结构：多租户实例管理池与安全上下文
type TenantInstance struct {
    TenantCode   string
    WriteDB      *sql.DB        // 排他写连接池 (MaxOpenConns = 1, 配合 BEGIN IMMEDIATE)
    ReadDB       *sql.DB        // 并发读连接池 (MaxOpenConns = 4, PRAGMA query_only = 1)
    UsedBytes    atomic.Int64   // 内存级实时物理字节占用计数器
    MaxQuotaBytes int64         // 配额上限字节数 (0 表示不限)
    WriteCounter atomic.Int64   // 累计写操作计数 (用于触发异步磁盘配额校准與脏备份判定)
    LastAccessed atomic.Int64   // 最后访问 UTC 时间戳 (用于 LRU 空闲连接回收)
    LastModified atomic.Int64   // 最后一次写事务时间戳 (用于静默租户跳过冗余备份)
    Status       string         // active, readonly_quota, suspended
}

type TenantManager struct {
    mu          sync.RWMutex
    masterDB    *sql.DB
    instances   map[string]*TenantInstance
    maxInstances int            // 最大常驻活跃租户池大小 (默认 128)
    dataRoot    string          // 默认 "data"
}

// 2. 专属超级管理员硬边界守卫 (仅允许 huxinkui 在主空间或持穿透令牌执行总控操作)
const MasterAdminUsername = "huxinkui"

func RequireMasterAdmin() gin.HandlerFunc {
    return func(c *gin.Context) {
        user := GetCurrentUser(c)
        tenantCode := c.GetString("tenant_code")
        // 严苛校验：用户名必须为 huxinkui，拥有 MasterAdmin 标志，且当前处于主控空间
        if user == nil || user.Username != MasterAdminUsername || !user.IsMasterAdmin || tenantCode != "default" {
            c.AbortWithStatusJSON(http.StatusForbidden, gin.H{
                "code":    "FORBIDDEN_MASTER_ADMIN_ONLY",
                "message": "权限越界：仅平台专属超级管理员 (huxinkui) 可访问多租户总控中枢",
            })
            return
        }
        c.Next()
    }
}

// 3. 动态租户路由、防横向越权与 huxinkui 跨空间穿透中间件
func TenantIsolationMiddleware(tm *TenantManager) gin.HandlerFunc {
    return func(c *gin.Context) {
        reqTenant := extractTenantCode(c) // 从 Header / Query / Cookie 提取并校验 ^[a-z0-9_]{3,32}$
        user := GetCurrentUser(c)         // 解析会话 Token

        if user != nil {
            // 情况 A: 超级管理员 huxinkui 发起跨租户穿透巡检
            if user.Username == MasterAdminUsername && user.IsMasterAdmin && reqTenant != "default" {
                impMode := c.GetHeader("X-Impersonate-Mode") // "readonly" 或 "readwrite"
                if impMode != "readwrite" && !isReadOnlyMethod(c.Request.Method) {
                    c.AbortWithStatusJSON(http.StatusForbidden, gin.H{
                        "code":    "IMPERSONATION_READONLY_GUARD",
                        "message": "当前处于超级管理员只读巡检模式，已拦截写操作以保护租户现场数据",
                    })
                    return
                }
                c.Set("is_impersonating", true)
                c.Set("impersonated_by", MasterAdminUsername)
            } else if user.TenantCode != reqTenant {
                // 情况 B: 普通租户试图访问其他租户或 default 主空间 -> 严厉阻断横向越权！
                c.AbortWithStatusJSON(http.StatusForbidden, gin.H{
                    "code":    "TENANT_ISOLATION_VIOLATION",
                    "message": "安全拦截：禁止跨租户空间访问数据！",
                })
                return
            }
        }

        // 加载目标租户物理沙箱实例 (自动触发懒加载 Schema 检查与 LRU 刷新)
        inst, err := tm.GetOrOpenTenant(reqTenant)
        if err != nil || inst.Status == "suspended" {
            c.AbortWithStatusJSON(http.StatusLocked, gin.H{"code": "TENANT_UNAVAILABLE", "message": "租户空间不存在或已被管理员冻结"})
            return
        }
        c.Set("tenant_instance", inst)
        c.Set("tenant_code", reqTenant)
        c.Next()
    }
}

六、 核心业务子系统与多租户架构的协同规范

在完善多租户物理隔离体系后，原 V1.2 的 12 大业务子系统全部运行在各自独立的租户数据库实例上下文中，实现真正的零干扰运行：

1. 单据自动编号序列器隔离：每个租户的 `document_sequences` 表完全独立，租户 A 与租户 B 在同一天开具的采购订单均可从 `PO-20261015-0001` 开始连续编号，互不抢占自增序列，亦不会暴露平台全局单据规模。

2. 高精度成本核算与往来核销事务隔离：每个租户内部的采购入库移动加权平均成本重算、销售订单库存预占锁定（Stock Reservation）以及到期日 FIFO 自动收付款核销，均在该租户专属的 `WriteDB` 上通过 `BEGIN IMMEDIATE` 排他事务独立执行。租户 A 进行万级明细盘点过账时，绝不阻塞租户 B 的毫秒级收银开单。

3. 软件商业授权与租户租期双层联动：在单机/私有化部署模式下，Ed25519 商业授权绑定宿主机硬件指纹；在多租户模式下，平台主库校验证书允许的最大租户开通数量（`max_tenants`），而超级管理员 huxinkui 可单独为每个子租户設定服务到期时间（`expire_at`）。当某租户合约到期时，仅将该租户降级为只读查询模式，保障租户随时导出历史报表与备份，不影响其他正常续费租户。
