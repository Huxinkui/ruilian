睿链进销存与往来管理系统
软件架构、功能与实现设计说明书
版本：V1.0定位：企业采购、销售、库存及往来账务一体化管理平台
一、软件名称与品牌定位
软件名称：睿链进销存与往来管理系统（简称“睿链”）。“睿”体现经营分析、智能决策与精细化管理，“链”体现采购、库存、销售、应收应付之间形成完整业务链路。该名称适合后续扩展到移动端、门店、供应链和BI分析等产品。
二、项目总体定位
系统面向批发、零售、贸易、经销、代理等企业，以商品为核心，以库存为基础，以采购与销售为业务驱动，以应收应付为经营闭环，形成采购、入库、库存、销售、出库、收付款、核销、经营分析的一体化平台。
三、总体技术架构
前端：Vue 3 + TypeScript + Vite + Pinia + Vue Router + Element Plus + ECharts。
后端：Go + Gin + GORM/Repository 分层架构，REST API，必要场景使用 WebSocket 推送。
数据库：PostgreSQL，金额采用 DECIMAL，数量采用 DECIMAL(18,4) 等精度字段。
缓存与任务：Redis（可选），用于会话、缓存、分布式锁及异步任务。
认证授权：JWT/Session + RBAC，支持菜单、按钮、数据、仓库及金额权限。
部署：Windows/Linux 均可，推荐应用服务、数据库、备份服务相互隔离。
四、功能架构
工作台：经营指标、销售/采购趋势、库存结构、应收账龄、待审核单据、预警中心。
基础资料：商品、分类、品牌、单位、规格型号、客户、供应商、仓库、库位、员工、业务员。
采购管理：采购订单、采购入库、采购退货、采购换货、采购价格、采购查询。
销售管理：批发、零售、委托代销、销售订单、销售出库、销售退货、销售换货、客户价格与折扣。
库存管理：库存余额、出入库、调拨、盘点、组装、拆分、批次、序列号、库存流水、上下限预警、呆滞库存。
往来管理：客户应收、供应商应付、收款、付款、预收、预付、核销、信用额度、账期、对账。
价格管理：基础价、批发价、零售价、客户等级价、客户专属价、数量阶梯价、促销价、历史价格。
报表中心：采购、销售、库存、毛利、客户、供应商、应收、应付及经营分析。
预警中心：库存不足、库存超限、呆滞、信用超额、应收逾期、应付到期、最低售价异常。
系统管理：用户、角色、权限、组织、参数、单据编号、日志、审计、数据字典、备份管理。
五、核心业务流程
采购：供应商 → 采购订单 → 采购入库 → 应付账款 → 付款 → 应付核销。
销售：客户 → 销售订单 → 销售出库 → 应收账款 → 收款 → 应收核销。
退货：原采购/销售业务 → 退货单 → 库存反向变动 → 应收/应付冲销或退款。
调拨：调出仓 → 调拨单 → 在途（可选）→ 调入仓。
盘点：理论库存 → 盘点单 → 实盘数量 → 差异审核 → 盘盈/盘亏流水。
委托代销：委托发货 → 委托库存 → 实际销售 → 代销结算 → 确认销售及应收。
组装/拆分：组件库存反向变化 + 成品库存正向变化，并形成成本追溯。
六、库存实现机制
库存采用“库存余额 + 库存流水 + 业务单据”三层模型。禁止业务人员直接修改库存余额；所有库存变化必须来源于审核后的业务单据，并生成 InventoryTransaction 流水。
库存维度：商品 + 仓库 + 库位 + 批次（必要时增加序列号）。
库存状态：现存、可用、锁定、在途、委托等。
并发控制：库存更新使用数据库事务和 SELECT ... FOR UPDATE 行级锁，防止并发超卖。
允许负库存由系统参数控制，默认不允许。
库存流水保存业务单号、业务类型、变动前数量、变动数量、变动后数量、操作人和时间。
成本建议采用移动加权平均，也可扩展批次成本。
七、往来账务实现
应收应付由业务单据产生，不允许通过修改余额的方式直接调账。
收款/付款形成独立单据，并通过核销关系关联一笔或多笔应收应付。
支持部分核销、批量核销、预收/预付、退款及退货冲账。
客户信用额度与账期在销售审核时实时检查。
账龄按到期日计算，支持未到期、1~30、31~60、61~90、91~180、180天以上等区间。
期初应收、期初应付、期初库存应作为初始化数据独立记录，避免伪造历史业务单据。
八、价格与折扣引擎
采用可配置价格规则引擎。推荐匹配优先级：客户+商品专属价 → 客户等级+商品价 → 数量阶梯价 → 商品销售价 → 商品指导价。价格规则支持生效时间、失效时间、适用客户、数量范围和最低销售价。后端负责最终价格计算，前端只负责展示。

十、单据与状态机
所有核心业务采用统一单据模型：单据头 + 单据明细 + 上下游关联 + 库存影响 + 往来影响 + 审核记录。
通用状态：草稿 → 待审核 → 已审核 → 执行中 → 已完成；异常状态包括已取消、已关闭。
审核后的单据原则上不可直接修改，如确需修改，应执行反审核/红冲/冲销等受控操作，并保留审计记录。
十一、数据安全与备份设计（重点）
系统必须把数据安全作为核心基础能力。备份不能只依赖数据库管理员手工执行，而应由系统建立自动备份、备份校验、保留策略、异地/异盘备份和恢复演练机制。
数据库自动备份：每日自动执行 PostgreSQL 逻辑备份或物理备份；重要环境建议采用物理基础备份 + WAL 归档，以实现更细粒度恢复。
WAL 持续归档：生产环境开启 PostgreSQL WAL 归档，将 WAL 文件复制到独立备份目录/备份服务器，降低故障时的数据丢失窗口。
备份至少三份：至少保留数据库本机备份、独立磁盘/服务器备份、异地备份三份副本；备份介质与数据库主机不能共用唯一存储。
自动校验：备份完成后计算 SHA-256 或使用数据库恢复校验机制，并随机抽取备份执行恢复验证，防止出现“有备份但备份不可恢复”。
保留策略：建议每日备份保留7~14天，每周备份保留8~12周，每月备份保留12个月；具体周期由企业要求配置。
故障保护：数据库异常时禁止继续写入可能破坏数据的一致性操作；应用层捕获数据库异常，事务失败自动回滚，并记录错误日志。
事务一致性：库存、应收、应付及业务单据之间涉及的数据修改必须在同一个数据库事务中完成，避免只更新一部分数据。
误删除保护：关键业务数据不建议物理删除，采用作废、关闭、冲销、软删除或归档机制，并保留操作审计。
备份管理界面：系统管理员可以查看最近备份时间、备份大小、备份状态、校验状态、备份路径及恢复验证结果。
恢复机制：提供数据库恢复操作说明和独立恢复脚本；生产环境恢复前先复制当前数据库，避免恢复操作二次覆盖现有数据。
十二、推荐备份架构
推荐采用“数据库主机 + 本地备份盘 + 独立备份服务器/对象存储”的结构。
数据库 → WAL实时归档 → 独立备份目录；同时每日生成完整备份 → 独立备份服务器；重要周期备份再同步到异地/对象存储。数据库服务器发生硬盘损坏时，不依赖数据库服务器本身恢复。
十三、恢复目标建议
RPO（可接受的数据丢失窗口）：生产环境建议控制在15分钟以内；采用WAL持续归档后可进一步缩短。
RTO（恢复目标）：普通故障建议在1~2小时内恢复核心业务，具体取决于数据库规模和服务器配置。
恢复优先级：数据库 → 后端服务 → 前端服务 → 文件/附件 → 报表缓存。
每月至少执行一次恢复验证，确认备份文件能够真正启动数据库并查询核心业务数据。
十四、异常与数据一致性保护
所有核心业务写操作采用数据库事务。
库存扣减前锁定库存记录并检查可用库存。
业务单据与库存流水、应收应付必须具备明确业务单号和关联ID。
接口支持幂等控制，避免网络重试造成重复入库、重复出库或重复收款。
关键接口使用 request_id/idempotency_key 防止重复提交。
后台异步任务必须具备失败重试、最大重试次数及死信/异常任务记录。
应用崩溃不会导致已提交事务的数据处于半完成状态；未提交事务由数据库自动回滚。
十五、日志与审计
记录登录、退出、增删改、审核、反审核、作废、库存调整、收付款、价格调整、信用额度调整、备份、恢复等关键操作。日志至少包含用户、时间、IP、业务单号、操作类型、结果以及必要的变更前后数据摘要。
十六、报表与分析
销售：销售日报/月报、商品排行、客户排行、业务员排行、毛利及退货分析。
采购：采购统计、供应商排行、采购价格趋势、采购退货。
库存：库存余额、库存金额、流水、周转、呆滞、上下限、盘点差异。
往来：客户应收、供应商应付、账龄、逾期、收付款及对账。
经营：销售额、采购额、库存金额、应收、应付、毛利、回款率和库存周转等。
十七、接口与前端实现原则
REST API 按业务域组织，例如 /api/purchase、/api/sales、/api/inventory、/api/ar、/api/ap。
统一响应结构、错误码、分页、排序和查询条件。
前端统一商品选择器、客户选择器、仓库选择器、金额输入和单据明细组件。
单据页面统一采用“基本信息 + 明细 + 汇总 + 操作”的布局。
重要数据实时刷新可通过WebSocket实现，但最终一致性以数据库为准。
所有金额由后端计算并再次校验，避免客户端篡改。
十八、系统最终业务闭环
基础资料 → 采购/销售 → 入库/出库 → 库存流水 → 应付/应收 → 付款/收款 → 核销 → 毛利与经营分析 → 预警与经营决策。
十九、建设后的核心特征
业务单据驱动库存，库存变化全程可追溯。
业务单据驱动应收应付，避免人工修改余额。
多仓库、多库位、多批次能力可扩展。
批发、零售、委托代销统一业务模型。
客户专属价格、等级价格、阶梯价格统一由价格规则引擎管理。
信用额度、账期、逾期和账龄统一管理。
库存上下限、呆滞库存、信用和账务异常统一进入预警中心。
数据库事务、幂等、日志、自动备份和恢复验证共同保障数据安全。
架构采用模块化设计，可继续扩展POS、会员、电商、财务、移动端、BI等能力。
二十、数据安全底线
任何情况下不得把“数据库服务器上的一个备份文件”视为完整的数据保护方案。生产系统至少需要具备：事务一致性、自动备份、WAL归档、独立备份介质、备份校验、保留策略、恢复脚本和定期恢复验证。只有能够成功恢复的数据，才是真正有效的备份。
二十一、软件授权与试用机制
系统增加独立的软件授权模块，用于控制软件试用期、正式授权及授权状态。当前版本采用“10天试用 + 永久授权 + 授权码人工生成/人工分发”的方式，不依赖在线授权服务器即可完成基础授权校验，同时为后续升级为在线授权、订阅授权和多终端授权预留接口。
21.1 授权模式
试用授权：软件首次安装或首次初始化后自动进入10天试用期。
正式授权：输入有效授权码后转为永久授权，永久授权不设置到期时间。
授权码分发：当前阶段由管理员/软件发行方在授权管理工具中手动生成授权码，再通过人工方式分发给客户。
离线可用：客户端正式授权后，即使没有互联网连接，也能够正常使用核心业务功能。
授权状态：未授权、试用中、试用到期、已授权、授权异常等。
21.2 试用期设计
首次运行软件时生成本机唯一的安装标识 Installation ID，并记录首次初始化时间。试用期从首次初始化时间开始计算10×24小时或按自然日计算10天，具体规则应固定在产品版本中，避免客户端通过修改系统时间绕过试用限制。推荐采用“首次启动时间 + 单调时间校验 + 最近运行时间”组合保护。
首次启动：创建本机 Installation ID、首次启动时间、最近运行时间。
正常运行：持续更新最近运行时间，禁止时间回拨。
检测到系统时间明显回退：标记授权异常并进入保护状态，不直接删除业务数据。
试用到期：禁止新增业务操作，但允许登录、查看授权状态、导出必要数据及输入正式授权码。
试用期间数据库和业务功能正常使用，不因为试用状态而改变数据结构。
21.3 永久授权设计
正式授权采用永久授权模型。授权成功后保存授权凭证及授权信息，并在本机完成签名验证。永久授权不依赖每次启动都连接授权服务器，因此适用于企业内网和离线环境。
授权类型：PERPETUAL。
授权状态：ACTIVE。
授权期限：永久，不设置 expire_at。
授权对象：绑定 Installation ID 或经过授权策略允许的机器标识。
授权信息至少包含产品标识、版本/版本范围、客户编号、授权类型、授权时间、机器绑定信息、随机序列号等。
授权码本身不直接保存为明文业务配置，系统保存授权结果和必要的签名验证数据。
21.4 授权码生成机制
当前版本不建设在线授权平台，采用独立的授权码生成工具人工生成并分发。为了防止普通用户伪造授权码，推荐采用非对称数字签名机制，而不是简单的固定格式字符串或MD5。
推荐流程：
发行方授权工具生成密钥对：私钥仅保存在发行方安全环境，公钥内置于客户端。
输入客户编号、Installation ID、产品版本范围、授权类型等信息。
授权工具使用发行方私钥对授权载荷进行数字签名。
生成可复制的授权码/授权文件。
客户在客户端“系统管理 → 软件授权”中输入授权码或导入授权文件。
客户端使用内置公钥验证签名；签名正确且授权对象匹配后激活永久授权。
客户端保存授权状态并记录授权操作日志。
21.5 推荐授权数据结构
授权载荷建议采用结构化JSON后再进行编码，并使用数字签名保护。例如：
product：产品标识，如 RUILIAN_ERP。
license_id：授权唯一编号。
customer_id：客户编号。
installation_id：授权绑定的安装标识。
license_type：PERPETUAL。
version_from / version_to：允许使用的软件版本范围。
issued_at：授权生成时间。
features：授权功能集合。
signature：发行方私钥签名。
21.6 授权数据库设计
license_local：本机授权状态。
license_activation_log：授权激活记录。
license_event_log：授权异常、试用到期、重新授权等事件。
system_installation：安装标识、首次运行时间、最近运行时间等本机信息。

21.8 功能控制策略
授权机制不应通过删除、锁死或破坏数据库来实现功能限制。授权失效时只控制业务入口，不得删除商品、客户、库存、往来账等数据。
试用中：全部功能正常使用。
试用到期：核心新增/修改业务受限，保留登录、查看、导出和授权激活能力。
正式授权：全部购买范围内功能正常使用。
授权异常：进入授权异常提示页面，同时保留数据查看和数据导出能力。
数据库备份、数据导出和恢复相关能力不得因为授权到期而被禁止，避免用户无法取回自己的经营数据。
21.9 防止简单修改时间绕过试用
由于当前采用离线试用模式，无法从根本上阻止拥有服务器管理员权限的用户篡改本机数据。因此，目标应是提高绕过成本，而不是宣称绝对防破解。建议采用以下组合机制：
Installation ID 与首次启动时间绑定。
保存最近一次正常运行时间，并检测时间回退。
关键授权状态进行完整性校验，例如HMAC或数字签名。
授权文件使用不可逆摘要/签名校验，避免直接修改数据库字段。
重要授权状态可写入独立配置区，并与数据库状态交叉校验。
授权相关异常全部写入操作日志。
不要把“是否授权”简单设计成一个可直接UPDATE的数据库布尔字段。
21.10 与数据备份体系的结合
授权信息属于系统运行配置的一部分，也需要纳入备份，但授权私钥绝不能进入客户数据库备份。
客户数据库备份：包含本机授权状态、授权编号及必要授权信息。
发行方授权私钥：仅保存在发行方授权工具环境，禁止随软件安装包、数据库备份或客户端配置分发。
恢复数据库：恢复后需要重新检查 Installation ID 与授权状态。
更换服务器/硬件：如果授权绑定Installation ID，应提供正式的“授权迁移/重新绑定”流程。
数据恢复不得因为授权信息损坏而导致业务数据丢失。

二十二、推荐最终系统架构补充
增加授权服务后，整体架构形成：
Web前端 → API Gateway → 业务服务层 → 数据访问层 → PostgreSQL。
业务服务层增加 LicenseService，负责试用状态、永久授权、授权校验和功能权限。
系统管理增加 License Management。
独立发行方工具 License Generator 负责人工生成授权码。
客户端内置授权公钥，发行方私钥不进入客户端。
BackupService 负责数据库备份、WAL归档、备份校验和恢复验证。
二十三、授权安全底线
授权系统的安全边界必须明确：客户端程序无法做到绝对防破解。正式授权应重点防止普通用户通过修改配置文件、数据库字段、系统时间或简单伪造字符串获得授权。最重要的安全措施是采用非对称数字签名，将发行方私钥与客户端彻底隔离。即使客户能够查看客户端代码，也无法仅凭客户端内置公钥生成合法永久授权码。
